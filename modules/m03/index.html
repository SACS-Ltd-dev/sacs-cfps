Networking Foundations for Cybersecurity

I'm not going to teach you networking the way a networking certification course would. I want you to follow a real conversation between two computers, packet by packet, until the whole exchange makes obvious sense.

What I want you to walk away with today

  • Explain how devices actually communicate across a network, from the cable to the application.
  • Work confidently with IP addressing, ports, routing, and the protocols you'll see constantly: TCP, UDP, DNS, HTTP, HTTPS, TLS.
  • Use basic troubleshooting tools without hesitating: ping, traceroute, ipconfig or ip, nslookup or dig, netstat or ss, curl.
  • Capture and interpret real network traffic in Wireshark.
  • Recognize a handful of common network security weaknesses when you see them in a capture.

How I want you thinking during this session

Do not just memorize what a protocol does. I'm going to keep asking you what the evidence in front of you means, what could be wrong with your conclusion, and what a professional would do next. If you can only demonstrate that a tool produced an output, I haven't done my job yet, and neither have you.

1. The OSI and TCP/IP Models

You've probably memorized the seven layers of OSI at some point. I'm not going to make you recite them today. What I actually want is for you to internalize the idea underneath the model: communication between two computers happens in layers, each one responsible for a different job, each one wrapping the layer above it in its own envelope.

Layer (simplified, TCP/IP view)JobExample
ApplicationWhat the user or program actually wants to doHTTP, DNS, SSH
TransportGetting data reliably (or quickly) between two programsTCP, UDP
InternetGetting data between two networksIP
LinkGetting data across one physical or local network segmentEthernet

Every packet you'll look at today is literally this: an HTTP request, wrapped in TCP, wrapped in IP, wrapped in Ethernet. When you open Wireshark for the first time today, that's exactly what you'll see stacked in front of you, one layer inside the next.

2. Ethernet, MAC Addressing, and ARP

Every network interface has a MAC address, a hardware address burned into it. On a local network, devices actually talk to each other using MAC addresses, not IP addresses directly. ARP (Address Resolution Protocol) is how a device discovers which MAC address belongs to which IP address on the local network.

The very first two packets you'll see in our capture are an ARP exchange: the client asking "who has 10.20.4.1", and the gateway answering "I do, and here's my MAC address." Nearly every capture you ever take will open with something like this. It's the network equivalent of a handshake before anyone actually speaks.

3. IP Addressing and Subnetting

An IP address identifies a device on a network. IPv4 addresses, the ones you'll work with almost exclusively in this programme, look like 10.20.4.31. Subnetting divides a network into smaller segments, which matters for security because it's one of your main tools for containing an incident. If ZTMB's branch network is properly subnetted, a compromised teller workstation in Ikeja shouldn't be able to freely reach the core banking database in Victoria Island.

I'm not going to turn this session into a subnetting mathematics drill. I want you comfortable reading an address like 10.20.4.0/24 and knowing, roughly, what that /24 means: 256 addresses, from 10.20.4.0 to 10.20.4.255. We'll go deeper on segmentation specifically in Module 8.

4. Routing and Switching

A switch moves traffic within a local network, using MAC addresses. A router moves traffic between networks, using IP addresses. When ZTMB's workstation talks to a server on the same local network, a switch handles it. When that same workstation talks to something on the internet, the traffic has to pass through a router, which is exactly why the gateway shows up in nearly every conversation you'll capture today.

5. TCP and UDP

These are the two transport protocols you need cold by the end of today.

Connection-oriented and reliable. Before any data moves, TCP performs a three-way handshake: SYN, SYN-ACK, ACK. You'll see this exact pattern at the start of every HTTP and TLS conversation in today's capture, and you'll see the mirror image, a FIN-based teardown, at the end. HTTP, HTTPS, and SSH all run over TCP, because they need reliable, ordered delivery.

Connectionless and fast, with no handshake and no guaranteed delivery. DNS runs over UDP for exactly this reason, a DNS query needs to be quick, and if one gets lost, the client just asks again. Notice in the capture that every DNS exchange is just two packets: query, then answer. No handshake at all.

6. DNS

DNS translates a domain name, something a human can remember, into an IP address, something a computer can route to. In our capture, the client asks the internal DNS resolver, 10.20.4.2, "what is the address for intranet.ztmb.local", and gets back 10.20.4.50.

Why I've built a DNS anomaly into today's capture

DNS is trusted by almost every firewall on almost every network, which makes it a favorite channel for attackers to hide command-and-control traffic or slowly exfiltrate data, a technique often called DNS tunneling. One of the clearest signs of this: DNS-style queries going somewhere other than your actual configured DNS resolver, especially with long, random-looking subdomains. Keep that sentence in mind for the lab.

7. DHCP

DHCP (Dynamic Host Configuration Protocol) is how a device automatically receives an IP address, gateway, and DNS server when it joins a network, rather than someone configuring it by hand on every machine. You won't see a DHCP exchange in today's capture, since our client already has its address, but you should know the term, since it comes up constantly in real network troubleshooting and in Module 13 when we discuss cloud networking.

8. HTTP, HTTPS, and TLS

HTTP is the protocol behind ordinary web browsing, and it's entirely readable in plaintext, which is exactly why our capture includes one plain HTTP request: so you can read every byte of it yourself, headers and all. HTTPS is HTTP wrapped inside TLS, which encrypts the conversation so that the request and response content can't be read by anyone intercepting the traffic.

Notice what TLS does and doesn't hide. In the banking session in our capture, you can still see the TCP handshake, the TLS handshake itself, and the IP addresses and ports involved. What you cannot see is the actual content of the request and response, which is exactly the point. TLS protects confidentiality and integrity, not the fact that a conversation happened at all.

9. NAT, VPNs, Proxies, and Firewalls

NAT (Network Address Translation) lets many internal devices share a small number of public IP addresses, which is why ZTMB's internal 10.20.4.x addresses never appear directly on the public internet. A VPN creates an encrypted tunnel between two points, commonly used by remote branch staff connecting back into ZTMB's internal network. A proxy sits between a client and a destination, often for filtering or logging. A firewall controls what traffic is allowed to pass, based on rules, and it's the single most common control you'll encounter across every module in this programme.

Session Summary

Every network conversation you'll ever investigate follows the same shape you saw today: address resolution, name resolution, a connection being established, content moving, and a connection closing. TCP and UDP behave differently and for good reasons. TLS encrypts content but not metadata. And the clearest anomalies are often not exotic at all, they're just traffic going somewhere, or behaving in a way, that doesn't match the pattern around it.
