1. How a Computer Actually Works

You don't need to become a computer engineer to work in security, but you do need a working mental model of four things: the CPU, memory, storage, and processes, because nearly every attack technique you'll study later abuses one of these four in some way.

ComponentWhat it doesWhy it matters to you
CPUExecutes instructionsMalware ultimately runs as instructions the CPU executes. High or unusual CPU usage is sometimes a clue.
Memory (RAM)Holds running programs and their data temporarilySome attacks live entirely in memory and never touch disk, which is why memory forensics exists as a discipline.
StorageHolds files and data persistentlyThis is where most of your evidence lives: logs, configuration files, and the files an attacker leaves behind.
ProcessesRunning instances of programsAn attacker's tools show up as processes. Knowing what's normal on a host is what lets you spot what isn't.

2. Filesystems

A filesystem is how an operating system organizes and keeps track of files on storage. Windows most commonly uses NTFS. Linux uses several, most often ext4. You don't need to memorize filesystem internals, but you do need to know your way around the directory structure, because that's where evidence and configuration live.

C:\Windows holds the operating system itself. C:\Windows\System32 holds core system binaries, and it's also a favorite disguise location for malware trying to blend in. C:\Users\<username> holds each user's personal files and, importantly, their AppData folder, which is where a huge amount of persistence and browser artifact evidence lives. C:\ProgramData holds application data shared across users.

/etc holds system-wide configuration files, including /etc/passwd and /etc/shadow for user accounts. /var/log holds the majority of the logs you'll care about. /home/<username> holds each user's personal files, and /tmp is a common (and often overlooked) place for an attacker to stage tools temporarily.

3. Users, Groups, and Permissions

Every action on a system happens as some user. Every file has an owner and a set of permissions controlling who can read, write, or execute it. Get comfortable with this idea now, because Module 4 builds an entire session on top of it.

Windows permissions are controlled through NTFS access control lists, attached to users and groups. net user lists local accounts, net localgroup administrators shows who has administrative rights on a machine. A user in the local Administrators group can do essentially anything on that machine, which is exactly why an unexpected addition to that group, like the one in tonight's lab evidence, deserves your attention.

Linux permissions follow the classic read, write, execute model for owner, group, and everyone else, shown as something like rwxr-xr--. chmod changes permissions, chown changes ownership. sudo -l shows what a user is permitted to run as another user, usually root. A user who can run anything as root through sudo is functionally an administrator, even without being in a group called "Administrators."

A weakness I want you able to spot immediately

Shared logins are one of the most common host security failures I see in real organizations, including plenty in Nigeria. If every teller at a branch logs into the same workstation account, you've lost the ability to tell which specific person did what. That single fact will matter enormously once we reach investigation and incident response later in this programme.

4. Processes, Services, and Persistence

A process is a running instance of a program. A service (Windows) or daemon (Linux) is a process designed to run in the background, often starting automatically when the machine boots. Persistence is how an attacker (or legitimate software) ensures something keeps running or keeps coming back, even after a reboot or a cleanup attempt.

ConceptWindowsLinux
List running processesGet-Process or Task Managerps aux
List servicesGet-Servicesystemctl list-units --type=service
Common persistence locationsRegistry Run keys, Scheduled Tasks, Servicescron jobs, systemd service units, shell profile files

You don't need to memorize every persistence technique today. Module 14 goes much deeper into this. For now, I just want you to recognize that "how does this thing keep running" is always a question worth asking.

5. Windows Event Logs and PowerShell

Windows records security-relevant activity in Event Logs, viewable through Event Viewer or queried with Get-WinEvent. The Security log is the one you'll use most in this programme. A handful of event IDs will carry you a very long way, and I want these memorized by the end of this session, not just recognized when you see them.

Event IDMeaning
4624An account successfully logged on
4625An account failed to log on
4672Special (administrative) privileges assigned to a new logon
4688A new process was created
4720A user account was created
4732A member was added to a security-enabled local group

PowerShell also keeps its own Operational log, which matters a great deal in practice, because a large share of real-world attacks against Windows environments use PowerShell at some stage. An encoded, hidden PowerShell command is one of the more reliable signals you'll learn to recognize this programme.

6. Linux Shell and System Logs

Where Windows stores logs in a structured binary format, Linux mostly writes logs as plain text, which honestly makes them a little friendlier to a beginner. /var/log/auth.log (Debian and Ubuntu family) or /var/log/secure (Red Hat family) record authentication activity: logins, sudo usage, SSH sessions. /var/log/syslog or /var/log/messages record general system activity.

Get comfortable with grep, tail -f, and less for reading these files. You will use all three constantly for the rest of this programme, well beyond this module.

7. SSH

SSH (Secure Shell) is how administrators remotely and securely manage Linux systems (and increasingly Windows too). It supports both password authentication and public key authentication, the latter being considerably stronger, since there's no password to brute-force or phish in the first place. In the Linux log you'll examine shortly, notice how clearly the log distinguishes a publickey login from a password login. That distinction alone tells you something about how well-managed a given account is.

8. Basic System Hardening

Hardening means reducing a system's attack surface: removing what you don't need, restricting what remains, and keeping what's left up to date. At this stage in the programme I just want a short mental checklist:

  • Remove or disable accounts nobody uses, especially default or vendor accounts.
  • Ensure every user has their own account. No shared logins.
  • Apply the principle of least privilege. Most staff do not need local administrator or root access.
  • Keep the operating system and installed software patched.
  • Disable services you don't actually use.

Live Lab Walkthrough: Host Investigation

Open your task sheet now.   2. Inspect running processes and services on both machines, and note anything that looks unfamiliar or unexpected.
  3. Identify at least one file or account with inappropriate permissions in the lab environment.
  4. Open the provided Windows and Linux log evidence and find every event tied to the account admin.temp on Windows and every event tied to the IP address 185.220.101.47 on Linux. Build a short timeline of what happened.
  5. Document one suspicious process or configuration you found, and explain, in your own words, why it's suspicious.

What I'm actually looking for

I want to see you connect specific log lines to specific conclusions. "Something suspicious happened" earns you very little credit. "The account admin.temp failed to log on five times in under a minute, then succeeded, then was immediately granted administrative privileges and used to create a new account added to the Administrators group, all within four minutes" is exactly the level of precision I'm training you toward.

Session Summary

A computer's CPU, memory, storage, and processes are the foundation everything else in security sits on top of. Windows and Linux organize users, permissions, processes, and logs differently, but the underlying questions you ask are identical on both: who did this, what ran, what changed, and where is the evidence. You now know where to look on either system.
